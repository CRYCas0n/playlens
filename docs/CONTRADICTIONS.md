# Аудит противоречий

**Дата:** 2026-09-06
**Метод:** каждое противоречие проверено против первичных данных (`docs/research-fixtures/`), а не против текста документов. Где перепроверка была возможна в текущей среде — она выполнена, и её результат приведён.

Формат: **Conflict / Source A / Source B / Actual evidence / Impact / Decision / ADR**.

---

## C-01. `limit` у эндпоинта рецензий критиков

| | |
|---|---|
| **Conflict** | Сколько critic-рецензий возвращает одна страница API |
| **Source A** | `BLUEPRINT.md §2.1.2`: «`limit` до **500** работает (проверено 50/100/200/500)» |
| **Source B** | `RELEASE0_VALIDATION.md §5.6`: critic-эндпоинт отдаёт **ровно 10** записей при любом `limit`; `offset`-пагинация работает, 4 страницы = 40 записей без дублей |
| **Actual evidence** | Фикстура `research-fixtures/metacritic/reviews_critic.json` снята с `limit=3` → `items=3`, `totalResults=93`; на трёх записях расхождение неразличимо. Release 0 проверял `limit=100` и получил 10 — более поздняя и более прицельная проверка. **B верно.** Для user-отзывов `limit` работает (`reviews_user.json`, `totalResults=6593`) |
| **Impact** | Бюджет обхода: Zelda со 150 рецензиями — 16 запросов вместо 1. При каталоге в тысячи игр это меняет стоимость crawl на порядок |
| **Decision** | Пагинатор **не доверяет** ни `limit`, ни константе. Он определяет фактический размер страницы по `len(items)` первого ответа и дальше шагает этим шагом; останавливается по `offset >= totalResults`, по пустой странице или по достижении cap. Один адаптер обслуживает оба эндпоинта корректно, даже если Metacritic завтра изменит поведение |
| **ADR** | ADR-005 |

## C-02. Что такое «New Releases»

| | |
|---|---|
| **Conflict** | ТЗ: «раздел New Releases, первые 20 игр, каждый новый день цикл начинается заново» — подразумевается поток новых игр |
| **Source A** | Исходное ТЗ §1 |
| **Source B** | `BLUEPRINT.md §2.1.2` (Расхождение №1) и `PRODUCT_BLUEPRINT.md §9`: фактически это `sortBy=-releaseDate&metaScoreMin=1&mcoTypeId=13`, `totalResults=18524`, список почти статичен; 18 из 20 игр завтра будут теми же |
| **Actual evidence** | `research-fixtures/metacritic/finder_new_releases.json`: `componentName=new-releases-carousel`, `sortBy=-releaseDate`, `metaScoreMin=1`, `totalResults=18524`. Подтверждено |
| **Impact** | Наивная реализация «каждый час → первые 20 → полный AI-пайплайн» ежедневно тратит LLM-бюджет на одни и те же игры. Это вопрос экономической жизнеспособности, а не оптимизации |
| **Decision** | Требование ТЗ выполняется **буквально** (New Releases обходится, максимум 20 новых игр за час, дневной цикл сбрасывается), но реальная работа расщеплена на **discovery** и **refresh**: захват игры на дату — атомарная вставка в `crawl_items(crawl_date, game_slug)`; дорогие downstream-этапы (отзывы, AI, similarity) запускаются только при изменении `source_fingerprint`, появлении новых отзывов или сдвиге оценок. Типичный повторный день для известной игры = 1 HTTP-запрос и 0 вызовов LLM |
| **ADR** | ADR-004, ADR-006 |

## C-03. Полнота offset-пагинации листинга

| | |
|---|---|
| **Conflict** | Можно ли последовательным обходом страниц получить полный каталог |
| **Source A** | ТЗ §2: «переходить к следующей странице при последующих запусках» — подразумевает, что обход даёт полноту |
| **Source B** | `BLUEPRINT.md §2.1.2` (Расхождение №2): два идентичных запроса при cache MISS вернули наборы, различающиеся **12 slug'ами из 24** |
| **Actual evidence** | Зафиксировано экспериментально в исследовании; вероятная причина — отсутствие вторичного tie-breaker'а при равных `releaseDate`. Из текущей среды не перепроверялось: сеть к Metacritic намеренно не использовалась |
| **Impact** | Курсор по страницам не гарантирует ни полноты, ни отсутствия дублей. Обещать «полный каталог» нельзя |
| **Decision** | Три меры: (1) дубли бесплатны — `ON CONFLICT DO NOTHING`; (2) курсор монотонный и двигается только после успешного захвата страницы; (3) **weekly sitemap reconciliation** (`games.xml`, 296 шардов) как независимый источник перечня slug'ов, с жёстким лимитом на количество добавляемых за прогон. Защита сохранена, частота — раз в неделю, чтобы reconciliation не превратилась в постоянный полный обход |
| **ADR** | ADR-004 |

## C-04. Параметр `?platform=`

| | |
|---|---|
| **Conflict** | Как получить per-platform данные |
| **Source A** | Естественное предположение: `?platform=` у composer-эндпоинта |
| **Source B** | `BLUEPRINT.md §2.1.2` (Расхождение №3): `?platform=` **игнорируется** и composer'ом, и HTML-страницей |
| **Actual evidence** | `composer_elden_ring.json`: `product.platforms[]` содержит `criticScoreSummary` по каждой платформе (PC 94, PS5 96, Xbox One `null`) — Metascore есть в одном вызове. Userscore на платформу в composer **отсутствует** |
| **Impact** | Полный сбор игры с N платформами = `1 + N` запросов минимум; Metascore берётся бесплатно из composer |
| **Decision** | Metascore per-platform — из `product.platforms[].criticScoreSummary`. Userscore per-platform — отдельный вызов `/reviews/metacritic/user/games/{slug}/platform/{p}/stats/web`. Детальные critic-счётчики (`positive/neutral/negative`) запрашиваются только для платформ, попавших в бюджет сбора отзывов |
| **ADR** | ADR-010 |

## C-05. `userScore: 0` — значение или отсутствие данных

| | |
|---|---|
| **Conflict** | ТЗ и техблюпринт хранят `userscore` как число; Release 0 показал, что 0 приходит вместо «нет данных» |
| **Source A** | `BLUEPRINT.md §6.3`: `userscore numeric(3,1)`, `CHECK BETWEEN 0 AND 10` |
| **Source B** | `RELEASE0_VALIDATION.md §5.5`: 4 игры из 20 (NBA 2K27, BioEden, Lou's Lagoon, Blood Dungeon) вернули `userScore: 0` при 1–3 оценках и нуле текстов. NBA 2K27: Metascore 79, Userscore 0 |
| **Actual evidence** | **Перепроверено в этой сессии по всем 21 корпусам `research-fixtures/release0/harvest/*.json`.** Все четыре случая `score == 0` имеют `reviewCount ∈ {1, 2, 3}` и `user_total_with_text == 0`. Минимальная *настоящая* низкая оценка в выборке — `0.5` при `reviewCount = 6382` (Diablo Immortal) и `0.6` при `reviewCount = 31276` (Warcraft III: Reforged). Ноль при большой выборке в данных **не встречается**; ноль при выборке ≤3 означает «нет данных» |
| **Impact** | Если вывести это как оценку, продукт сообщает заведомо ложное — и именно на свежих релизах, то есть на главной странице |
| **Decision** | Оценка — не число, а **значение со статусом**. Правило в одном месте (`app/domain/scores.py`): `unavailable`, если `review_count == 0`; `unavailable`, если `score == 0` **и** `review_count < USERSCORE_ZERO_MIN_RATINGS` (20); иначе `valid`. Независимо от этого — флаг `low_sample` при `review_count < 20`. Сырое значение и счётчик **всегда сохраняются**; правило влияет только на подачу. В UI `unavailable` рендерится как `—` / «Not rated». В сортировках такие игры уходят в конец при **обоих** направлениях |
| **ADR** | ADR-002 |

## C-06. Симметричная вёрстка «3 плюса / 3 минуса»

| | |
|---|---|
| **Conflict** | Фиксированное число пунктов в резюме |
| **Source A** | `PRODUCT_BLUEPRINT.md §13, §15, US-008`: «3 плюса, 3 минуса, вывод» |
| **Source B** | `RELEASE0_VALIDATION.md §4.2, §7.1` (**БЛОКИРУЮЩЕЕ**): 5 из 9 провалившихся блоков — «что не нравится» у высокооценённых игр |
| **Actual evidence** | Перепроверено: `harvest/elden-ring.json` → `critic_stats: {score: 96, reviewCount: 86, positiveCount: 86, neutralCount: 0, negativeCount: 0}`. Заполнить три минуса честным путём физически невозможно |
| **Impact** | Шаблон провоцирует галлюцинацию ровно там, где продукт больше всего рискует репутацией — на самых известных играх |
| **Decision** | Количество claims определяется **evidence, а не вёрсткой**: 0–5 на секцию. Пустая секция — легитимный и информативный результат, рендерится честной формулировкой («Critics raise almost no objections: 86 positive reviews, none negative»), а не натянутым пунктом. `min_items` в схеме отсутствует; валидатор дропает неподтверждённые claims **после** генерации |
| **ADR** | ADR-008 |

## C-07. `filterBySentiment` как источник истины

| | |
|---|---|
| **Conflict** | Можно ли считать бакеты Metacritic тональностью текста |
| **Source A** | `PRODUCT_BLUEPRINT.md §16`: «Sentiment analysis отбрасываю целиком… Используем их разметку как вход для резюме» |
| **Source B** | `RELEASE0_VALIDATION.md §5.1`: бакеты построены **на оценке, а не на тексте**. Пять паттернов загрязнения: политический бомбинг не по теме (8 из 24 отрицательных у Cyberpunk PS4), ироничные «10/10» («jogo de merda» с оценкой 10 у Gollum), встречный бомбинг (Forspoken), оценка против текста (RDR2: 0 и 1 с текстом «The best game I've ever played»), спам |
| **Actual evidence** | Подтверждено конкретными отзывами в `research-fixtures/release0/corpus/` |
| **Impact** | Пайплайн, доверяющий бакетам, на Gollum выдаст в «что нравится игрокам» — «шедевр, игра года». Одна такая карточка уничтожает доверие |
| **Decision** | Бакеты используются как **страты выборки**, но не как ground truth. Перед суммаризацией корпус проходит **фильтр согласованности оценки и текста** — детерминированный, без LLM: отзыв исключается, если знак текста устойчиво противоречит знаку оценки, если текст короче порога, если это дубликат по хэшу, или если он не про игру по эвристике. Число исключённых — метрика качества данных, видимая в мониторинге и в provenance («Compressed from N of M indexed reviews»). Отменяет `PRODUCT_BLUEPRINT §16` **в части фильтрации**; собственный sentiment как продуктовая фича по-прежнему не делается |
| **ADR** | ADR-007, ADR-008 |

## C-08. Порог «<20 отзывов — вердикт не генерируем»

| | |
|---|---|
| **Conflict** | Единый порог для обеих аудиторий, считаемый по числу оценок |
| **Source A** | `PRODUCT_BLUEPRINT.md §14`: «<20 отзывов → вердикт не генерируется» |
| **Source B** | `RELEASE0_VALIDATION.md §5.4, §7.5`: считать надо **по числу отзывов с текстом**. Onimusha: 77 пользовательских оценок, из них только 10 с текстом |
| **Actual evidence** | Перепроверено по `harvest/`: `onimusha-way-of-the-sword` PS5 — `user_stats.reviewCount = 77`, `user_total_with_text = 10`. Симметрично: `nba-2k27` — 5 critic-рецензий, `bioeden` — 4; это качественные тексты изданий, из которых резюме сделать можно. Единый порог 20 отрезал бы обе стороны |
| **Impact** | Слишком высокий порог для критиков обнуляет фичу на инди и свежих релизах; слишком низкий для игроков даёт вердикт по спаму |
| **Decision** | Пороги **асимметричны и считаются по текстам после фильтра C-07**: critic — `>= 5` рецензий с текстом; user — `>= 20` отзывов с текстом. Обоснование асимметрии: critic-рецензия — курируемый текст издания, в разы длиннее и без бомбинга; пять таких рецензий информативнее ста пользовательских «10/10 огонь». Объяснение gap'а требует обеих сторон выше порога **и** gap `>= 7` пунктов на оси 0–100. Пороги вынесены в конфиг |
| **ADR** | ADR-009 |

## C-09. Изменяемость корпуса отзывов

| | |
|---|---|
| **Conflict** | Резюме ссылается на позицию в массиве отзывов |
| **Source A** | `BLUEPRINT.md §10.4`: `input_fingerprint` есть, но неизменяемого снапшота, на который ссылаются claims, нет |
| **Source B** | `RELEASE0_VALIDATION.md §6.1`: после пересборки корпуса нумерация сдвинулась; скрипт нашёл 4 битые ссылки, **а остальные ссылки формально проходили проверку, но указывали на другие отзывы** |
| **Actual evidence** | Прямо задокументировано в отчёте прогона; корпуса в `research-fixtures/release0/corpus/` используют позиционные ID `[C00]` / `[U00]` |
| **Impact** | Главная механика доверия продукта («покажи, на чём основано») молча указывает в никуда. Это хуже отсутствия ссылок |
| **Decision** | Корпус — **неизменяемый версионированный снапшот**: `review_snapshots` + `snapshot_reviews(snapshot_id, evidence_ref, review_id, position)`. `evidence_ref` (`C00`, `U17`) присваивается один раз при построении и больше не меняется. Резюме хранит `snapshot_id`; claims ссылаются на `evidence_ref` **внутри своего снапшота**. Пересборка корпуса создаёт новый снапшот и не трогает старые резюме — ссылки не могут разъехаться. Детерминированный порядок: `(kind, published_on NULLS LAST, dedupe_key)` |
| **ADR** | ADR-007 |

## C-10. Даты отзывов в корпусе

| | |
|---|---|
| **Conflict** | Модель делает temporal-выводы без дат |
| **Source A** | Формат корпуса Release 0: `[C00] 90 \| Atomix \| текст` — **даты нет** |
| **Source B** | `RELEASE0_VALIDATION.md §4.3, §5.2, §7.3` (**БЛОКИРУЮЩЕЕ**): Redfall — единственный не подтверждённый вывод PV2; паттерн «мнение изменилось после патча» встретился в 3 играх из 20 |
| **Actual evidence** | Перепроверено: в `corpus/cyberpunk-2077__playstation-4.txt` строки отзывов дат не содержат, хотя в `harvest/*.json` поле `date` присутствует у обоих типов отзывов. То есть данные были, а до модели не доехали |
| **Impact** | Самый частый содержательный тип объяснения gap'а либо не генерируется, либо генерируется догадкой |
| **Decision** | Дата — обязательное поле каждой записи корпуса. В промпте — правило: любой temporal claim обязан опираться на даты процитированных отзывов. **Валидатор проверяет это машинно**: claim с `claim_type = temporal` проходит, только если даты его evidence образуют интервал не меньше `TEMPORAL_MIN_SPAN_DAYS` (30). Не прошедший claim удаляется |
| **ADR** | ADR-008 |

## C-11. Кто пишет вердикт: арифметика или модель

| | |
|---|---|
| **Conflict** | Главное предложение на странице игры |
| **Source A** | `design/README.md §3 п.5` (**non-negotiable**): «The verdict sentence is **derived, not generated**… **Do not replace it with model output**» |
| **Source B** | `PRODUCT_BLUEPRINT.md §6.4, §16, DEFINITION OF MVP п.6`: «Platform-aware вердикт» назван killer feature и отнесён к AI-функциям |
| **Actual evidence** | `PRODUCT_BLUEPRINT.md §16` сам пишет про этот вердикт: риск галлюцинаций «низкий… числовая часть — арифметика, не генерация». Источники расходятся меньше, чем кажется |
| **Impact** | Если вердикт генерирует модель, он может противоречить числам прямо над собой — худший из возможных дефектов доверия |
| **Decision** | **Дизайн выигрывает, продуктовая цель достигается полностью.** Вердикт — детерминированная функция `verdict_line(critic, user)`, чистая, покрытая табличными тестами, без LLM и без AI-дисклеймера. Platform-awareness добавляется **тоже арифметикой**: вторая производная строка сравнивает выбранную платформу с лучшей («On PlayStation 4 critics rate this 29 points lower than on PC»). Все *объяснительные* утверждения остаются за AI — в своих блоках, с evidence и provenance |
| **ADR** | ADR-012 |

## C-12. Платформа: глобальный контекст сессии или фильтр

| | |
|---|---|
| **Conflict** | Где живёт выбор платформы |
| **Source A** | `PRODUCT_BLUEPRINT.md §4 (Journey 6), §10, US-004`: платформа — **глобальный контекст**, селектор в шапке, игры без платформы скрываются |
| **Source B** | `design/UX_SPEC.md §3`, `design/COPY.md §2`: в топбаре — brandmark, nav, поиск, Monitoring, тема. **Селектора платформы нет.** Платформа — фильтр каталога и секция `By platform` на странице игры |
| **Actual evidence** | ТЗ §7 требует «фильтрация по платформе» — это фильтр каталога. Глобального контекста ТЗ не требует |
| **Impact** | Новый контрол в топбаре ломает IA дизайна; отказ от платформенного контекста ослабляет главный дифференциатор |
| **Decision** | Компромисс, зафиксированный явно: **новых контролов в топбаре нет**. Требование ТЗ закрывает фильтр каталога. Продуктовая ценность закрывается «предпочитаемой платформой»: пользователь помечает платформу прямо в блоке `By platform` на странице игры, значение живёт в `localStorage` и делает три вещи — (1) предвыбирает фильтр платформы в каталоге, (2) подсвечивает свою строку в `By platform`, (3) включает вторую, платформенную строку вердикта (C-11). Та же ценность в рамках IA дизайна |
| **ADR** | ADR-010 |

## C-13. Нормализация Userscore к шкале 0–100

| | |
|---|---|
| **Conflict** | Приводить ли шкалы к одной |
| **Source A** | `PRODUCT_BLUEPRINT.md §12, §27 (R15)`: «**Никогда не приводить к одной шкале** — это исказит смысл» |
| **Source B** | `design/README.md §3 п.1` (**non-negotiable**): Userscore «always normalised to 0–100 (×10) before comparison. Display the player number in its native `8.9` form» |
| **Actual evidence** | Обе стороны решают одну проблему (пользователь путает 86 и 8.9) разными средствами |
| **Impact** | Без общей оси невозможны gap как число, сортировка «biggest gap» и консенсус-блок — второй по силе дифференциатор продукта |
| **Decision** | **Дизайн выигрывает и снимает возражение продукта**: отображается нативное значение (`8.9`) с подписью аудитории; сравнение и все производные величины считаются на оси 0–100; рядом с блоком сравнения **всегда** присутствует поясняющая подпись. Опасение «исказит смысл» относилось к подмене отображения, а не к вычислению gap'а |
| **ADR** | ADR-002 |

## C-14. Похожие игры в MVP

| | |
|---|---|
| **Conflict** | Входят ли похожие игры в обязательный объём |
| **Source A** | Исходное ТЗ §6: обязательное требование, только из своей БД, кликабельные |
| **Source B** | `PRODUCT_BLUEPRINT.md §17, DEFINITION OF MVP`: «нельзя включать в P0», качество — функция размера каталога |

## C-19. Celery + Redis как фоновая инфраструктура

| | |
|---|---|
| **Conflict** | Нужны ли брокер и планировщик отдельными сервисами |
| **Source A** | `BLUEPRINT.md §4, §13, Приложение A.3`: Celery 5.4 + Redis, 3 очереди, Beat |
| **Source B** | Тот же `BLUEPRINT.md §13.1` и §20.3: «`result_backend = None` — результаты в своей таблице `jobs`, не в Redis»; «корректность не зависит от Redis»; «Потеря Redis не приводит к дублям»; вся дедупликация и все гарантии уже сделаны констрейнтами PostgreSQL |
| **Actual evidence** | Внутреннее противоречие блюпринта: он вводит Celery и одновременно объявляет, что не полагается ни на один из его durable-механизмов. Реальная нагрузка — ~20 игр в час, упирающаяся в rate limiter источника |

Интерфейс `JobQueue` сохранён — возврат к Celery возможен без изменения бизнес-логики. **Честная оговорка:** отсутствие Docker/Redis на машине разработки сделало это решение и практически необходимым; но оно принято на архитектурных основаниях и было бы принято без него |

## C-22. PostgreSQL-специфичные конструкции

| | |
|---|---|
| **Conflict** | Насколько глубоко привязываться к PostgreSQL |
| **Source A** | `BLUEPRINT.md §6`: `CREATE TYPE ... AS ENUM`, `integer[]` + GIN, `pg_trgm`, `pgvector`, `xmax = 0` |
| **Source B** | Требование задания §48/§75: каждая фаза оставляет проект в **проверяемом** состоянии. В среде разработки PostgreSQL недоступен (нет Docker, 384 МБ свободного места) |
| **Actual evidence** | Проверено в этой сессии: SQLite 3.45.1 поддерживает partial unique indexes, `ON CONFLICT DO NOTHING RETURNING`, `UPDATE ... RETURNING`, `NULLS LAST` и generated columns — то есть **все** конструкции, на которых держатся гарантии дедупликации |
| **Impact** | Без второго диалекта интеграционные тесты не запускаются нигде, и репозиторный слой уезжает непроверенным |
| **Decision** | **PostgreSQL 16 — продакшн-СУБД; SQLite — поддерживаемый диалект для разработки и тестов.** Схема ограничена общим подмножеством: enum'ы — `VARCHAR + CHECK` (заодно снимает боль миграций enum в PG), массивы-роллапы заменены полу-джойном по индексированной `game_platforms` (скалярные роллапы `best_*` / `lead_*` сохранены), `xmax = 0` заменён на портируемое различение вставки и обновления. Единственная диалект-зависимая операция — **поиск по названию** — изолирована в одном методе репозитория с двумя реализациями. Тот же интеграционный набор гоняется против обоих диалектов; прогон против PostgreSQL — обязательная validation-задача (**OQ-V1**) |
| **ADR** | ADR-018 |
