# ADR-007 — Неизменяемый версионированный снапшот корпуса отзывов

**Статус:** принято · 2026-09-06
**Отменяет:** `BLUEPRINT.md §10.4` в части «достаточно `input_fingerprint`»
**Связанные противоречия:** C-09, C-07, C-10

## Context

Release 0 нашёл дефект, который невозможно обнаружить чтением кода:

> «Блок Cyberpunk 2077 (PC) был написан по первой версии корпуса. Затем корпус пересобрали,
> нумерация ID сдвинулась. Скрипт проверки нашёл 4 ссылки на несуществующие отзывы.
> **Хуже того: остальные ссылки того блока формально проходили проверку, но указывали
> на другие отзывы.**» — `RELEASE0_VALIDATION.md §6.1`

Ссылки на источник — главная механика доверия продукта (`PRODUCT_BLUEPRINT.md` JTBD J9,
принцип 3 «Ни одного утверждения без основания»). Молча разъехавшаяся ссылка хуже
отсутствующей: она выглядит проверяемой и не является таковой.

Второй дефект того же прогона (§6.2): первая версия выборки обрезала пользовательские отзывы
на 65 записях в порядке «сначала положительные», из-за чего **весь отрицательный бакет
отбрасывался**, а рецензии критиков брались как «первые 45 по убыванию оценки» — то есть
только самые высокие. Резюме получились бы систематически хвалебными, а метрика — ложно высокой.

Третий (§5.1): бакеты `filterBySentiment` построены на оценке, а не на тексте, и на играх
с экстремальными рейтингами оценка не отражает содержание.

Четвёртый (§7.3): в корпус не передавались даты, из-за чего единственный неподтверждённый
вывод PV2 (Redfall) был получен догадкой.

## Decision

**Корпус, переданный модели, — неизменяемый версионированный артефакт.**

### Схема

```sql
review_snapshots (
  id, game_id, platform_id, kind,           -- critic | user
  content_hash,        -- sha256 по упорядоченному списку (dedupe_key, body_hash, score, date)
  ordering_version,    -- версия алгоритма упорядочивания, входит в content_hash
  sampling_version,    -- версия алгоритма выборки и фильтра
  review_count,        -- сколько попало в снапшот
  candidate_count,     -- сколько было до фильтра и выборки
  rejected jsonb,      -- {too_short: 12, score_text_mismatch: 8, duplicate: 3, off_topic: 2}
  date_min, date_max,  -- диапазон дат корпуса
  built_at,
  UNIQUE (game_id, platform_id, kind, content_hash)
)

snapshot_reviews (
  snapshot_id, evidence_ref, review_id, position,
  PRIMARY KEY (snapshot_id, evidence_ref),
  UNIQUE (snapshot_id, review_id)
)
```

`evidence_ref` — `C00…C99` / `U00…U99`, присваивается **один раз** при построении снапшота
и никогда не меняется. Резюме хранит `snapshot_id`; каждый claim ссылается на `evidence_ref`
**внутри своего снапшота**. Пересборка корпуса создаёт **новый** снапшот с другим
`content_hash`; старые резюме продолжают указывать на свой — ссылки не могут разъехаться.

### Детерминированный порядок

Сортировка кандидатов: `(published_on NULLS LAST ASC, dedupe_key ASC)`.
Стабильна, не зависит от порядка выдачи API и от порядка строк в БД. Версия алгоритма
(`ordering_version`) входит в `content_hash`: изменение сортировки даёт новый снапшот,
а не тихую подмену смысла существующих ссылок.

### Конвейер построения

```
reviews (БД)
   |  1. отбор кандидатов: kind + platform + текст непустой
   v
   |  2. ФИЛЬТР КАЧЕСТВА (детерминированный, без LLM)
   |     - len(body) < CORPUS_MIN_CHARS (80)            -> too_short
   |     - дубликат по body_hash внутри игры            -> duplicate
   |     - несогласованность оценки и текста            -> score_text_mismatch
   |     - не про игру (эвристика)                      -> off_topic
   v
   |  3. СТРАТИФИЦИРОВАННАЯ ВЫБОРКА
   |     страты: тональность (по ОЦЕНКЕ, как страта, не как истина)
   |             x временные окна (до/после медианы дат)
   |     квоты пропорционально реальному распределению,
   |     но с полом MIN_STRATUM_SHARE (15%) на каждую непустую страту
   |     ранг внутри страты: 0.45*длина + 0.30*свежесть + 0.15*экстремальность + 0.10*полезность
   v
   |  4. упорядочивание, присвоение evidence_ref, content_hash
   v
review_snapshots + snapshot_reviews
```

### Фильтр согласованности оценки и текста

Дешёвый, детерминированный, объяснимый. Считаем лексический полярный счёт текста
(словарь позитивных/негативных маркеров + отрицания + эмодзи-нейтрализация) и сравниваем
знак со знаком оценки. Отзыв исключается только при **устойчивом** противоречии:
оценка в верхнем терциле при явно негативном тексте или наоборот, при длине текста выше
порога надёжности. Все исключения считаются и попадают в `rejected`.

Это не sentiment-анализ как продуктовая фича (продуктовый блюпринт справедливо отказался
от неё), а **гигиена входа**: без неё резюме Gollum содержит «шедевр, игра года»
в разделе «что нравится игрокам».

### Формат записи корпуса, передаваемого модели

```
[C07] score=90 | date=2020-12-07 | pub=Atomix | <текст, control-chars вычищены, обрезан по CORPUS_MAX_REVIEW_CHARS>
[U31] score=3  | date=2023-04-11 | <текст>
```

**Дата присутствует всегда** — это блокирующее требование Release 0 §7.3.

### Провенанс, доходящий до UI

`review_snapshots.candidate_count` и `rejected` отдаются в API и рендерятся в provenance-футере:
«Compressed from 187 of 214 indexed player reviews» — пользователь видит, что часть корпуса
отфильтрована, а оператор видит, сколько именно и почему.

## Alternatives considered

| Вариант | Почему не выбран |
|---|---|
| Только `input_fingerprint` без снапшота (позиция блюпринта) | Отпечаток отвечает «изменился ли вход», но не даёт стабильных адресов внутри входа. Именно на этом сломался Release 0 |
| Ссылаться на `reviews.id` напрямую | Работает, но делает промпт зависимым от суррогатных ключей БД, а корпус — невоспроизводимым при переносе. `evidence_ref` короче в промпте (экономия токенов) и явно ограничен снапшотом |
| Хранить полный текст корпуса в снапшоте | Дублирует таблицу `reviews` в разы. Снапшот хранит **порядок и состав**, тексты берутся по FK |
| Не фильтровать корпус, доверять бакетам источника | Проверено Release 0: даёт ироничные «10/10» в разделе «что нравится». Один такой блок уничтожает доверие |
| Фильтровать корпус вторым вызовом LLM | Дорого (умножает стоимость), недетерминированно, и сам фильтр становится источником галлюцинаций |
| Выборка «первые N» | Проверено Release 0 §6.2: систематически смещает резюме |

## Consequences

- Резюме не может ссылаться на отзыв, которого не было в его снапшоте — это проверяется
  валидатором машинно (ADR-008), а не доверием к модели.
- Появляется дешёвый ответ на вопрос «нужно ли перегенерировать»: если новый `content_hash`
  равен старому — вход не изменился, LLM не вызывается (и это дополнительно защищено
  уникальным индексом).
- История резюме воспроизводима: по `snapshot_id` можно точно восстановить, что видела модель.
- Стоимость: одна дополнительная таблица связей и построение снапшота (~O(n log n) в памяти
  на игру-платформу, n ≤ 500).

## Risks

| Риск | Митигация |
|---|---|
| Лексический фильтр ошибочно выбрасывает валидные отзывы | Порог срабатывания консервативный (только устойчивое противоречие + минимальная длина); `rejected` виден в мониторинге как метрика качества данных; словарь и пороги в конфиге. Release 0 §6.3 прямо предупреждает, что лексический детектор годится как грубый фильтр, а не как метрика приёмки |
| Многоязычные отзывы (в корпусе есть pt, it, es) | Фильтр применяется только при уверенном срабатывании; неопознанный язык не является причиной исключения. Язык записывается в `reviews.language_hint` для будущей работы |
| Рост числа снапшотов | Ретенция: снапшоты, на которые не ссылается ни одно резюме и старше `SNAPSHOT_RETENTION_DAYS` (90), удаляются задачей обслуживания |
