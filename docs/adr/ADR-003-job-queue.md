# ADR-003 — Фоновая обработка: очередь в PostgreSQL вместо Celery + Redis

**Статус:** принято · 2026-09-06
**Заменяет:** `BLUEPRINT.md §4, §13, Приложение A.3 (ADR-0003 «Celery вместо arq/RQ»)`
**Связанные противоречия:** C-19, C-18

## Context

ТЗ §11 требует «архитектуру фоновой обработки: scheduler + queue + workers», разделение
задач на синхронные/асинхронные/retryable/идемпотентные, и §12 — retry, backoff, timeout,
rate limit, idempotency, переживание падения воркера.

Блюпринт выбрал Celery 5.4 + Redis. При этом он же, в §13.1 и §20.3, зафиксировал:

- `result_backend = None` — результаты пишутся в собственную таблицу `jobs`, не в Redis;
- «Мониторинг должен показывать историю, связи run → job → game, причины ошибок и переживать
  перезапуск Redis. Redis result backend с TTL этого не даёт»;
- «Redis-лок нужен для эффективности; **корректность обеспечивают уникальные констрейнты**»;
- «Полная потеря Redis не приводит к дублям».

То есть архитектура уже объявила PostgreSQL источником истины для состояния задач и
отказалась опираться на durable-механизмы Celery. Celery остался поставщиком четырёх вещей:
брокера, Beat, политики ретраев и `acks_late`.

Профиль нагрузки: 20 игр в час, ~12 HTTP-запросов на игру, упирающиеся в rate limiter
источника (2 rps). Блюпринт сам пишет (Приложение A.3): «реальная нагрузка упирается
в rate limiter, а не в воркер».

## Decision

**Очередь, планировщик, ретраи и журнал — в PostgreSQL. Redis и Celery из состава убраны.**

Таблица `jobs` (которая по блюпринту обязана существовать в любом случае) становится
очередью:

```
захват      UPDATE jobs SET status='running', worker_id=?, lease_expires_at=now()+ttl,
                            started_at=now(), attempts=attempts+1
            WHERE id = (SELECT id FROM jobs
                        WHERE status IN ('queued','retrying') AND queue = ?
                          AND (next_retry_at IS NULL OR next_retry_at <= now())
                        ORDER BY priority DESC, queued_at
                        LIMIT 1 FOR UPDATE SKIP LOCKED)
            RETURNING *
```

- **Идемпотентность** — `UNIQUE(jobs.idempotency_key)`; повторная постановка той же задачи
  физически невозможна.
- **Переживание падения воркера** — аренда (`lease_expires_at`) + heartbeat + reaper,
  возвращающий просроченные задачи в `queued`. Это эквивалент `acks_late`, но без
  `visibility_timeout` и без второго хранилища.
- **Retry/backoff** — колонки `attempts`, `max_attempts`, `next_retry_at`; экспоненциальный
  backoff с полным джиттером считается в коде классификации ошибок.
- **Dead-letter** — статус `dead` при исчерпании попыток, отдельно от `failed` (можно
  повторить руками) и от `skipped` (предусловие не выполнено — не ошибка).
- **Планировщик** — отдельный лёгкий процесс: cron-выражения из конфига, постановка задачи
  с `idempotency_key = f"{name}:{slot}"`, поэтому дубли расписания невозможны даже при
  двух запущенных планировщиках.
- **Rate limiter** — token bucket строкой в таблице `rate_limits(host, tokens, updated_at)`,
  атомарный `UPDATE ... RETURNING`. Точен при N воркерах, в отличие от процесс-локального.
- **События и SSE** — append-only `job_events`; `job_events.id` **является** SSE
  `Last-Event-ID` (см. ADR-013).
- Интерфейс `JobQueue` (`enqueue / claim / complete / fail / heartbeat`) отделён от
  реализации: возврат к Celery или переход на другой брокер не затрагивает сервисы.

Очереди остаются логическими (`crawl`, `enrich`, `ai`) — это колонка `queue` и параметр
запуска воркера `--queues`, что даёт ту же изоляцию «дорогих» задач.

## Alternatives considered

| Вариант | Плюсы | Минусы | Итог |
|---|---|---|---|
| **Celery + Redis** (блюпринт) | Зрелость, готовые ретраи, Beat, огромная база знаний | Два инфраструктурных сервиса и контейнер; durable-состояние всё равно дублируется в `jobs`; два источника правды, которые могут разойтись; Redis теряет очередь при рестарте без AOF | Отклонено |
| arq / Dramatiq / RQ | Легче Celery | Та же дупликация состояния, та же зависимость от Redis, меньше зрелости | Отклонено |
| Внешний managed-брокер (SQS и т.п.) | Не наша операционная нагрузка | Внешняя зависимость и стоимость ради 20 задач в час; оффлайн-разработка невозможна | Отклонено |
| **Очередь в PostgreSQL** | Один источник правды; durable по построению; очередь, история и мониторинг — одна транзакция; `FOR UPDATE SKIP LOCKED` — стандартный, проверенный паттерн; минус 2 сервиса | Свои ~250 строк кода; polling вместо push; при очень высокой нагрузке упирается в БД | **Выбрано** |

## Why

1. **Устраняется дупликация состояния.** В варианте с Celery «задача выполнена» существует
   в двух местах (брокер и `jobs`), и они могут разойтись при падении между `ack` и `COMMIT`.
   В варианте с БД смена статуса задачи и запись её результата — одна транзакция.
2. **Требование ТЗ «переживание перезапуска» выполняется сильнее.** Очередь в PostgreSQL
   с fsync переживает то, что Redis без AOF теряет.
3. **Мониторинг становится тривиальным и честным.** Глубина очереди — `COUNT(*)`,
   а не `LLEN` по каналу, который не совпадает с журналом.
4. **Простота, требуемая заданием §63.** Минус два сервиса, минус две зависимости,
   минус целый класс ошибок.
5. Стоимость polling'а: один индексный запрос раз в `WORKER_POLL_INTERVAL` (1 с) на воркера.
   При двух воркерах это 2 запроса в секунду — на три порядка ниже, чем нагрузка от
   пользовательского трафика, который эта же БД обслуживает.

**Честная оговорка.** Отсутствие Docker и Redis на машине разработки (свободно 384 МБ)
делало вариант с Celery невыполнимым и непроверяемым здесь. Это ускорило решение, но не
определило его: аргументы 1–4 самодостаточны, и решение было бы тем же при неограниченных
ресурсах.

## Consequences

- `docker-compose.yml`: `postgres`, `migrate`, `api`, `worker`, `scheduler`. Redis нет.
- Задержка подхвата задачи — до `WORKER_POLL_INTERVAL` (1 с). Для часового цикла нерелевантно.
- Ручной запуск (`POST /admin/crawl/run`) ставит задачу и возвращает `202` — синхронной
  работы в HTTP-запросе по-прежнему нет (Rule 5 ТЗ §33).
- Появляется собственный код очереди, который обязан быть покрыт тестами на конкурентность:
  два воркера не должны захватить одну задачу; просроченная аренда должна возвращаться.
- Перенос на Celery в будущем — реализация `JobQueue` + замена `worker.py`; сервисы не меняются.

## Risks

| Риск | Митигация |
|---|---|
| Свой код очереди содержит ошибку | Интеграционные тесты на конкурентный захват, на истечение аренды, на исчерпание попыток, на идемпотентность; малый объём (~250 строк), покрытый целиком |
| `FOR UPDATE SKIP LOCKED` отсутствует в SQLite | Диалектная ветка: в SQLite захват сериализуется одним `UPDATE ... WHERE id = (SELECT ... LIMIT 1) RETURNING`, что корректно, поскольку SQLite и так сериализует записи. Одна изолированная функция (ADR-018) |
| Рост нагрузки упрётся в БД | Индексы `jobs(status, queue, priority, queued_at)`; при необходимости — партиционирование `job_events` и вынос очереди. Порог далеко за пределами требований |
| Долгая задача блокирует прогресс | Мягкий таймаут задачи + heartbeat аренды; reaper снимает зависшую |
