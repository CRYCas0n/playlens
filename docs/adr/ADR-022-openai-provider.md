# ADR-022 — Поддержка OpenAI как второго LLM-провайдера

**Статус:** принято · 2026-09-07
**Уточняет:** ADR-008 (evidence-driven резюме)

## Context

Владелец положил в `.env` ключ OpenAI, ожидая, что сервис будет использовать ChatGPT
вместо Claude. Кода для этого не было: существовал ровно один адаптер, `anthropic_client`,
а переменная `OPENAI_API_KEY` никем не читалась и молча игнорировалась.

Молчание — худшая часть этой истории. Приложение стартовало бы, ключ бы не использовался,
и резюме остались бы в состоянии «в процессе» без единого сообщения о причине.

Абстракция для этого уже существовала. `LLMProvider` — протокол, а не класс, и `ADR-008`
формулировал это прямо: «смена провайдера или модели — изменение в контейнере, а не в
логике суммаризации». Оставалось проверить, правда ли это.

Оказалось правдой: адаптер, ветка в контейнере, одно значение в `Literal`. Ни строчки в
`summary_service`, `validator` или промптах не изменилось.

## Decision

**`LLM_PROVIDER=openai` поддерживается наравне с `anthropic`.** Ключ живёт в
`LLM_API_KEY`, а не в `OPENAI_API_KEY`: имя переменной не должно меняться при смене
провайдера, иначе смена провайдера перестаёт быть однострочной.

### Без SDK

Адаптер говорит с REST API через `httpx`, который уже есть в зависимостях. Пакет `openai`
дал бы retry-логику, которая у нас своя, и типизированную поверхность, из которой мы
используем три поля — в обмен на ещё одну зависимость, которую надо обновлять. Проект
держит 9 runtime-зависимостей, и это не случайность.

Побочная выгода: адаптер полностью тестируется через `httpx.MockTransport` — 26 тестов
без ключа, без сети и без пакета.

### Tool calling, а не `response_format: json_schema`

Строгий JSON-режим OpenAI запрещает `additionalProperties` у объектов, а `aspect_verdicts`
— это именно словарь «аспект → вердикт». Параметры функции такого ограничения не имеют,
и через них файл ложится один в один на anthropic-клиент вместо того, чтобы требовать
собственной операции на схеме.

### Три отличия в обработке ошибок — и все обоснованные

| Ситуация | Anthropic | OpenAI | Почему по-разному |
|---|---|---|---|
| Ответ не сходится со схемой | permanent | **retryable** | Anthropic принуждает схему: расхождение постоянно. У OpenAI параметры функции — рекомендация, ответ стохастический, повторный запрос обычно проходит |
| 401 | retryable (по коду) | **permanent, с именем настройки** | Повторять отклонённый ключ шесть раз не поможет никому |
| 404 | retryable | **permanent, с именем модели** | То же: неизвестная модель сама не появится |

### Неизвестная метка аспекта → `other`

Найдено на первом же настоящем прогоне: `gpt-4o-mini` устойчиво возвращал
`aspect: "value"` — значение вне пятнадцати допустимых. Из-за этого терялось **целое
корректное резюме**: правильные утверждения, правильные ссылки на отзывы, всё
выбрасывалось из-за одной метки категории.

Аспект — это ярлык для группировки на странице и для профиля похожести. Читатель
действует по тексту утверждения и по ссылкам на отзывы, и **они валидируются отдельно и
строго**. Схема, которая жертвует целым ради самого неважного своего поля, расставляет
приоритеты неправильно.

Поэтому:
* неизвестный аспект **утверждения** становится `other`;
* неизвестный ключ в `aspect_verdicts` **отбрасывается**, а не сводится к `other` —
  это словарь, и слияние двух неизвестных меток молча потеряло бы один из вердиктов.

Решение уровня схемы, поэтому действует для обоих провайдеров.

### Проверка соответствия модели провайдеру

`LLM_MODEL=claude-sonnet-5` с `LLM_PROVIDER=openai` — опечатка, которая иначе всплыла бы
как 404 на первой генерации, то есть часами позже и в виде «сломанной фичи». Валидатор в
`Settings` ловит это при импорте и называет обе стороны.

Отвергаются только явно чужие пары. Незнакомое имя модели пропускается: новые выходят
постоянно, и отказ стартовать из-за неизвестного имени был бы хуже решаемой проблемы.

## Alternatives considered

| Вариант | Почему не выбран |
|---|---|
| Сказать «OpenAI не поддерживается» | Работа ограниченная и предсказуемая, а абстракция под неё уже была. Отказ был бы отказом от того, ради чего протокол и писался |
| Читать `OPENAI_API_KEY` | Тогда имя переменной зависит от провайдера, и смена провайдера перестаёт быть одной строкой. Переменная закомментирована в `.env` с объяснением |
| Пакет `openai` | +1 зависимость ради трёх полей и retry, который уже есть |
| `response_format: json_schema` со `strict` | Требует хирургии над схемой из-за `aspect_verdicts`, и результат расходился бы с anthropic-клиентом |
| Отбрасывать невалидное утверждение вместо всего резюме | Это уже делает валидатор — но по доказательствам, а не по формату. Молча удалять вывод модели на уровне парсинга значило бы прятать проблему от метрики отбраковки |

## Consequences

* Переключение провайдера — две строки в `.env`, без изменения кода.
* Стоимость считается по обоим прайс-листам и попадает в те же поля `summaries`, поэтому
  дневной лимит `AI_DAILY_COST_LIMIT_USD` работает одинаково.
* Проверено на настоящем API: 6 игр Release 0, **PV1 87.2%** (порог 80), **PV2 100%**
  (порог 85), $0.0074 на прогон с `gpt-4o-mini`.
* `_llm_model_matches_provider` — четвёртый валидатор в `Settings`, и все четыре
  существуют по одной причине: поймать ошибку конфигурации раньше, чем она станет
  загадочным поведением через час работы.

## Risks

| Риск | Митигация |
|---|---|
| Прайс-лист устареет | Неизвестная модель считается в $0 — недооценка стоимости, а не перерасход. Лимит расходов считает по записанным суммам, поэтому недооценка означает более щедрый лимит, а не бесконтрольную трату. Стоит сверять при смене модели |
| `gpt-4o-mini` слабее на evidence-дисциплине | Измеряется: `make release0` печатает PV1. На выборке из 6 игр — 87.2%. Полный прогон на 20 играх и слепая человеческая оценка остаются в `OPEN_QUESTIONS` |
| Два адаптера разойдутся | Оба реализуют один протокол и покрыты симметричными наборами тестов; расхождения в классификации ошибок перечислены в таблице выше и являются намеренными |
