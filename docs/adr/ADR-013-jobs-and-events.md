# ADR-013 — Мониторинг: журнал событий как источник SSE

**Статус:** принято · 2026-09-06
**Заменяет:** `BLUEPRINT.md §14.1` (ADR-0004) в части транспорта событий
**Связанные противоречия:** C-18, C-23, C-19

## Context

ТЗ Bonus 2 требует показывать: статус краулера и воркеров, текущий job, количество
обработанных / успешных / неуспешных, ошибки, очередь, время последнего и следующего запуска,
длительность, историю запусков, кнопку `Run now`. И отдельно: «мониторинг не должен требовать
перезагрузки страницы».

Блюпринт предложил SSE поверх Redis pub/sub: воркер публикует событие в канал, FastAPI
ретранслирует. При этом там же (§14.3) написано: «Все события **сначала пишутся в
`job_events`** (durable), затем публикуются в Redis. Если Redis упадёт, история не потеряется,
а после reconnect клиент доберёт по `Last-Event-ID`».

То есть durable-поток уже существует, а pub/sub — только средство доставки.
После решения убрать Redis (ADR-003) нужен ответ, что доставляет события.

## Decision

**SSE читает напрямую из append-only таблицы `job_events`. `job_events.id` — это `Last-Event-ID`.**

```
GET /api/v1/monitoring/stream?run_id=<optional>
  1. отдаёт событие `snapshot` с полным MonitoringStatus
  2. дальше в цикле: SELECT * FROM job_events WHERE id > :cursor [AND crawl_run_id = :run]
                     ORDER BY id LIMIT 200
  3. каждое событие: `id: <row id>\nevent: <type>\ndata: <json>\n\n`
  4. пусто -> sleep(SSE_POLL_INTERVAL_MS = 400)
  5. heartbeat `: ping` каждые SSE_HEARTBEAT_S (15) против таймаутов прокси
  6. reconnect: браузер сам присылает `Last-Event-ID`, курсор берётся оттуда
```

Свойства, которых нет у pub/sub:

- **Ни одно событие не теряется.** Клиент, отключившийся на минуту, при переподключении
  получает всё пропущенное — не «то, что успели опубликовать», а всё, что записано.
- **Порядок гарантирован** монотонным `id`, а не порядком доставки.
- **Дубликаты невозможны** — курсор строго возрастает.
- **История и поток — одни и те же данные.** Нельзя получить ситуацию «в ленте событие есть,
  в журнале нет».
- Нет единственной точки отказа: падает БД — падает всё, но это уже не «мониторинг лёг
  отдельно от сервиса».

Цена: задержка до `SSE_POLL_INTERVAL_MS` (400 мс) и один индексный запрос на клиента раз
в 400 мс. `SSE_MAX_CLIENTS` (50) ограничивает нагрузку.

### Fallback на polling

Фронтенд: если `EventSource` не открыл соединение за 5 с или получил `error` трижды подряд —
переключается на `GET /api/v1/monitoring/status` раз в 3 с. Индикатор соединения в UI:
`● Live` / `◐ Reconnecting` / `○ Polling`. Требование «без перезагрузки страницы»
выполняется в обоих режимах; SSE **не является** единственным способом получить состояние.

### Модель событий

```
job_events(id bigserial, ts, level, event, message,
           crawl_run_id, job_id, game_id, worker_id, stage, data jsonb)
```

Типы: `run.started` · `run.progress` · `run.finished` · `job.started` · `job.finished` ·
`game.synced` · `reviews.synced` · `snapshot.built` · `summary.generated` ·
`summary.rejected` · `similarity.computed` · `youtube.*` · `budget` · `error` · `heartbeat`.

События пишутся **вне** бизнес-транзакции (autocommit): откат бизнес-логики не должен
стирать запись о том, что она провалилась.

### Что показывает страница (покрытие требований ТЗ)

| Требование ТЗ | Источник |
|---|---|
| статус сервиса | health-агрегат: БД, планировщик (heartbeat), внешние API (circuit state) |
| статус воркеров | `SELECT worker_id, MAX(heartbeat_at)` из `worker_heartbeats` |
| текущий job | `jobs WHERE status='running'` + последнее событие активного прогона |
| обработано / успешно / ошибок / пропущено | счётчики `crawl_runs` за текущий прогон и за сегодня |
| очередь | `COUNT(*) GROUP BY queue, status` + возраст самой старой задачи |
| текущая страница Metacritic | `crawl_days.browse_page`, `phase` |
| последний / следующий запуск | `MAX(crawl_runs.started_at)`; следующий — из cron-выражения планировщика |
| длительность | `crawl_runs.duration_ms`, p50/p95 по `jobs.duration_ms` за 24 ч |
| ошибки | `job_events WHERE level IN ('warning','error') ORDER BY ts DESC` |
| история запусков | `crawl_runs ORDER BY started_at DESC LIMIT 20` |
| `Run now` | `POST /api/v1/admin/crawl/run` → 202 / 409 |
| stage strip дизайна | `job_events.stage` агрегированный по текущему прогону |

Плюс продуктовые метрики качества данных сверх ТЗ (`PRODUCT_BLUEPRINT §19`):
`% игр с полными данными`, `% с резюме`, средний возраст данных, доля отбракованных claims,
расход LLM за сутки.

### Доступ

Чтение `GET /api/v1/monitoring/*` открыто (требование ТЗ; секретов нет; сообщения проходят
редактор секретов). Любая мутация — `X-Admin-Token`. Страница живёт на `/admin/monitoring`,
в главной навигации отсутствует, помечена `noindex`. См. ADR-019.

## Alternatives considered

| Вариант | Почему не выбран |
|---|---|
| SSE поверх Redis pub/sub (блюпринт) | Требует Redis (ADR-003), теряет события при отключении подписчика, и всё равно нуждается в доборе из `job_events` при reconnect — то есть в том, что здесь является единственным механизмом |
| WebSocket | Поток односторонний. Даёт неиспользуемый обратный канал и апгрейд протокола в прокси |
| Только polling (позиция продукта) | Требование ТЗ «без перезагрузки страницы» выполняется, но real-time теряется, а стоимость SSE над готовым журналом мала |
| LISTEN/NOTIFY PostgreSQL | Убирает задержку, но требует отдельного соединения на процесс, не работает в SQLite, теряет события при отключении и всё равно нуждается в доборе. Возможная будущая оптимизация поверх того же курсора |

## Consequences

- Задержка событий до 400 мс — незаметна на странице мониторинга.
- `job_events` растёт; ретенция `EVENTS_RETENTION_DAYS` (30) чистится задачей обслуживания.
  Курсор SSE может указывать на удалённую строку — обрабатывается как «начать с текущего конца».
- Индекс `job_events(id)` (PK) и `job_events(crawl_run_id, id)` — этого достаточно.
- Тестировать SSE можно без сети и без брокера: записали событие → клиент получил.

## Risks

| Риск | Митигация |
|---|---|
| Много клиентов → много запросов | `SSE_MAX_CLIENTS`; интервал 400 мс; запрос по PK-индексу |
| Долгая транзакция задерживает видимость событий | События пишутся autocommit'ом вне бизнес-транзакции |
| Клиент с очень старым `Last-Event-ID` получит лавину | `LIMIT 200` на итерацию; при разрыве больше `SSE_MAX_BACKLOG` отдаётся свежий `snapshot` и курсор сдвигается в конец |
