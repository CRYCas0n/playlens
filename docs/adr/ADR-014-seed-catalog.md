# ADR-014 — Seed-каталог: тот же конвейер, другой источник

**Статус:** принято · 2026-09-06
**Связанные противоречия:** C-15, C-14

## Context

ТЗ описывает сбор новых релизов. Продуктовый блюпринт (§5, §28, PQ2, риск R13) называет
seed-набор известных игр **блокирующим** требованием и обосновывает так:

> Aha moment наступает, когда пользователь открывает игру, **которую он знает лично**,
> и видит вердикт, совпадающий с его опытом. Краулер по ТЗ собирает новинки, а проверять
> пользователь будет Elden Ring, Baldur's Gate 3, GTA V, The Witcher 3.
> Пустой поиск = мгновенный уход, второго шанса нет.

Дополнительно seed чинит две другие вещи: похожие игры (не из чего выбирать в маленьком
каталоге — §17) и демонстрацию заказчику.

Ограничение задания §53: **никаких hardcoded production data**. Список из 500 названий
в коде — именно это.

Ограничение ADR-004: полный обход каталога с Metascore при 20 играх в час — ~38 суток.

## Decision

**Seed — не отдельная подсистема и не набор данных, а тот же discovery-конвейер,
запущенный один раз с другим параметром сортировки.**

```
python -m app.cli seed --limit 500 [--min-metascore 1] [--dry-run]
```

Что делает:

1. Идёт в `finder/metacritic/web` с `sortBy=-metaScore&metaScoreMin=1&productType=games`,
   постранично, с тем же rate limiter'ом, тем же circuit breaker'ом и теми же парсерами.
2. Кладёт найденные slug'и в `crawl_items` с `crawl_date = today` и **`source='seed'`**,
   через тот же `ON CONFLICT DO NOTHING`.
3. Ставит те же задачи `game.sync`, которые дальше сами тянут отзывы, снапшоты, резюме
   и похожие игры.

Отличий от обычного прогона ровно два: сортировка (`-metaScore` вместо `-releaseDate`)
и то, что бюджет задаётся аргументом, а не `CRAWL_MAX_GAMES_PER_RUN`. Seed **не обходит**
дедупликацию и не пишет в БД ничего, чего не написал бы обычный обход.

`crawl_items.source` делает происхождение каждой игры видимым в мониторинге:
`new_releases` / `browse:page=N` / `sitemap` / `seed` / `manual`.

## Alternatives considered

| Вариант | Почему не выбран |
|---|---|
| Захардкоженный список 500 slug'ов в коде или JSON-файле | Прямо запрещено заданием §53. Устаревает, требует ручного сопровождения, и это данные в репозитории кода |
| Дамп БД с готовыми играми в репозитории | То же самое, плюс лицензионные вопросы к текстам отзывов |
| Не делать seed, ждать 38 суток обхода | Продукт нельзя показать и нельзя проверить: поиск по «Elden Ring» пуст, похожие игры пусты. Риск R13 продуктового блюпринта реализуется полностью |
| Увеличить `CRAWL_MAX_GAMES_PER_RUN` до 200 | Нарушает явное требование ТЗ «максимум 20 за прогон» (C-26) |
| Seed отдельным пайплайном с упрощённой обработкой | Второй путь записи данных = второй набор багов и вторая точка расхождения. Один конвейер — одно поведение |

## Consequences

- Seed на 500 игр: 500 × (1 composer + N stats + страницы отзывов) при 2 rps ≈ несколько часов
  фоновой работы. Запускается один раз при развёртывании, не блокирует API.
- Каталог сразу содержит узнаваемые игры → работают поиск, похожие и демонстрация.
- Стоимость AI на seed: 500 игр × ~1.5 резюме. `AI_USE_BATCH` (если поддержан провайдером)
  и дневной лимит стоимости ограничивают расход; при исчерпании лимита задачи откладываются,
  а не падают.
- В README и в `docs/RUNBOOK.md` seed — часть процедуры первого запуска.

## Risks

| Риск | Митигация |
|---|---|
| Seed перегружает источник | Тот же rate limiter (2 rps) и тот же circuit breaker; прерывается и продолжается с любого места, потому что состояние в `crawl_items` |
| Seed съедает дневной бюджет LLM | `AI_DAILY_COST_LIMIT_USD` + отложенные задачи; seed растягивается на несколько суток и это нормально |
| «500» — произвольное число | Аргумент CLI. Продуктовый блюпринт называет диапазон 200–500; выбран верх, потому что похожие игры выигрывают от объёма |
| Игры seed'а конкурируют за дневной слот с New Releases | Не конкурируют: seed ставит задачи напрямую, минуя `CRAWL_MAX_GAMES_PER_RUN`, и это явная ручная операция оператора |
