# ADR-004 — Архитектура краулера: state machine, дневной цикл, sitemap-сверка

**Статус:** принято · 2026-09-06
**Уточняет:** `BLUEPRINT.md §7`
**Связанные противоречия:** C-02, C-03, C-26, C-16

## Context

Требования ТЗ §1–§2, §17:

1. Запуск примерно раз в час.
2. Сначала New Releases, затем страницы browse с сортировкой New; можно продолжать со
   следующей страницы при последующих запусках.
3. В начале каждого нового календарного дня цикл начинается заново.
4. **За один hourly run — максимум 20 игр**, которые ещё не обрабатывались сегодня.
5. Уже существующую игру — обновить, не дублировать.

Факты, меняющие наивную реализацию:

- New Releases — не поток новинок, а `sortBy=-releaseDate&metaScoreMin=1` с
  `totalResults = 18 524`; 18 из 20 игр завтра будут теми же (C-02).
- Порядок выдачи `finder` при равных `releaseDate` недетерминирован: два идентичных запроса
  разошлись на 12 slug'ов из 24 (C-03). Offset-пагинация не гарантирует полноты.
- Блюпринт задал `CRAWL_MAX_GAMES_PER_RUN = 40`, что прямо противоречит требованию «20» (C-26).

## Decision

### 1. Явная state machine, а не скрипт

```
                    +-----------+
  listing --------> | discovered|
                    +-----+-----+
                          | claim (INSERT ON CONFLICT DO NOTHING)
                          v
                    +-----------+   бюджет исчерпан / дубль
                    |  queued   |------------------------------> skipped
                    +-----+-----+
                          v
                    +-----------+
                    | fetching  |--- permanent error ----------> failed
                    +-----+-----+
                          v
                    +-----------+
                    | normalized|
                    +-----+-----+
                          v
                    +-----------+     fingerprint не изменился
                    | persisted |--------------------+
                    +-----+-----+                    |
                          | reviews нужны            |
                          v                          |
                +-------------------+                |
                | reviews_fetching  |--- fail --> partial (игра остаётся SUCCESS)
                +---------+---------+                |
                          v                          |
                +-------------------+                |
                | snapshot_built    |                |
                +---------+---------+                |
                          v                          |
                +-------------------+                |
                | summary_pending   |                |
                +---------+---------+                |
                          v                          |
                +-------------------+  claims не прошли валидацию
                | summary_generated |------------------> summary_rejected
                +---------+---------+                |
                          v                          |
                +-------------------+                |
                |    validated      |                |
                +---------+---------+                |
                          v                          v
                    +-----------------------------------+
                    |            completed              |
                    +-----------------------------------+
```

Состояния `crawl_items.status` — подмножество, видимое оператору:
`pending · processing · done · failed · skipped`. Полная стадия каждой игры внутри прогона
видна через `jobs.job_type` + `job_events.stage`.

### 2. Дневной цикл и бюджет

- Дата фиксируется **на старте прогона** (`CRAWL_TIMEZONE`, дефолт UTC) и не меняется внутри.
  Смена даты внутри прогона проверяется на границе каждой страницы; прогон завершается чисто.
- `crawl_days(crawl_date PK, phase, new_releases_done, browse_page, browse_offset,
  browse_pages_done, browse_exhausted, release_date_watermark, games_claimed)` — курсор дня.
- `CRAWL_MAX_GAMES_PER_RUN = 20` (**требование ТЗ**, не 40). Значение конфигурируемо,
  но HTTP-параметр ручного запуска **не может его превысить** — только уменьшить.
- Фаза A — New Releases (`limit = NEW_RELEASES_LIMIT = 20`). Если New Releases отдал меньше
  20 *новых* игр, остаток бюджета тратится на фазу B в том же прогоне.
- Фаза B — browse: `finder?sortBy=-releaseDate&metaScoreMin=1&productType=games`,
  `offset = (page-1) * BROWSE_PAGE_SIZE`. Курсор двигается **всегда** после успешно
  обработанной страницы, даже если все её элементы оказались дублями — иначе краулер
  застревает на странице, полностью состоящей из уже известных игр.
- Курсор **не двигается**, если источник недоступен: прогон завершается статусом `partial`,
  следующий tick повторит ту же страницу.

### 3. Захват игры на дату

```sql
INSERT INTO crawl_items (crawl_date, game_slug, source, crawl_run_id, status, lease_expires_at)
VALUES (:date, :slug, :source, :run, 'processing', :lease)
ON CONFLICT (crawl_date, game_slug) DO NOTHING
RETURNING id;
```

Вернулась строка — игра наша на сегодня. Не вернулась — уже взята (этим же прогоном,
прошлым часом, другим воркером). Это и есть требование «максимум 20 ещё не обработанных
сегодня»; см. ADR-006.

### 4. Три независимых барьера против двойного запуска

1. Advisory-lock/строчная блокировка `crawl_days` на время открытия прогона (эффективность).
2. Partial unique index: `CREATE UNIQUE INDEX ... ON crawl_runs (status) WHERE status='running'`
   — второй активный прогон физически невозможен.
3. `UNIQUE(crawl_items.crawl_date, game_slug)` — даже если бы два прогона запустились,
   игра не обработается дважды.

Потеря любого одного барьера не приводит к дублям.

### 5. Weekly sitemap reconciliation

`games.xml` → 296 шардов по ~1000 URL. Раз в неделю (воскресенье 03:00, `RECONCILE_CRON`):
скачиваем шарды с тем же rate limit, извлекаем slug'и, диффим с `games.mc_slug`, кладём
первые `RECONCILE_MAX_NEW` (дефолт 2000) отсутствующих в `crawl_items` с `source='sitemap'`.

Периодичность выбрана так: `<changefreq>weekly</changefreq>` в самом sitemap; 296 запросов
при 2 rps ≈ 2.5 минуты — приемлемо раз в неделю и неприемлемо ежедневно. Лимит на добавление
не даёт reconciliation превратиться в постоянный полный обход.

### 6. Eligibility

Обе фазы discovery используют `metaScoreMin=1` (см. ADR-015). Sitemap отдаёт всё подряд,
поэтому игры без Metascore в базу всё же попадают — и это нормально: модель и UI их
полностью поддерживают как `Not rated`.

## Alternatives considered

| Вариант | Почему не выбран |
|---|---|
| «Каждый час первые 20 → полный пайплайн» (буквальное чтение ТЗ) | 18 из 20 игр те же самые каждый день; ежедневный прогон LLM по одним и тем же данным. Экономически нежизнеспособно |
| Дедупликация в приложении (множество обработанных в памяти/Redis) | Не переживает рестарт, не работает при N воркерах, и корректность зависит от кода, а не от констрейнта |
| Отказаться от sitemap-сверки | Оставляет каталог с гарантированными дырами из-за недетерминированной пагинации. Защита стоит 2.5 минуты в неделю |
| Ежедневная sitemap-сверка | 296 запросов в день ради изменений, которые сам источник декларирует как weekly |
| Курсор двигать только при найденных новых играх | Краулер застревает на странице из одних дублей и никогда не доходит до конца каталога |

## Consequences

- Типичный час: 1 запрос листинга + до 20 задач `game.sync`. Средняя длительность tick'а —
  единицы секунд, потому что tick только **ставит** задачи.
- Типичный «повторный» день для известной игры: 1 HTTP-запрос (composer), 0 вызовов LLM.
- Полный обход каталога с Metascore: 18 524 / 20 в час ≈ 38 суток. Ускоряется seed-обходом
  (ADR-014) и увеличением `CRAWL_MAX_GAMES_PER_RUN` при явном решении владельца.
- `crawl_days` даёт мониторингу «текущую страницу Metacritic» — требование ТЗ §10.

## Risks

| Риск | Митигация |
|---|---|
| Прогон падает после 7 из 20 игр | 7 = `done`, 13 = `processing` с истёкшей арендой; reaper (каждые 5 минут) возвращает их в `pending` и переставляет `game.sync`. Прогон = `failed`, следующий tick продолжает |
| Смена схемы листинга | `SchemaDriftError` → прогон `partial`, курсор не двинут, метрика и событие; при превышении порога — авто-переключение на `HtmlSource` |
| Sitemap-сверка добавляет тысячи игр без оценок | Лимит `RECONCILE_MAX_NEW`; такие игры хранятся как `Not rated` и не попадают в дефолтный листинг каталога по фильтру score-band |
| Часовой пояс «нового дня» | `CRAWL_TIMEZONE=UTC` по умолчанию, зафиксировано как OQ-N1 (не блокирующее) |
