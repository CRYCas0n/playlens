# ADR-008 — Evidence-driven резюме: claim, evidence, машинная валидация

**Статус:** принято · 2026-09-06
**Отменяет:** `PRODUCT_BLUEPRINT.md §13/§15/US-008` в части «ровно 3 плюса и 3 минуса»
**Связанные противоречия:** C-06, C-07, C-10

## Context

Release 0 прогнал 20 игр, 835 рецензий критиков и 1 025 пользовательских отзывов, 207 отдельных
утверждений. Результаты:

- **PV1 claim-level: 83.6% (173/207)**, на корпусах ≥20 отзывов — 81.9%. Порог 80% пройден.
  Главный вывод: суммаризатор **не водянист** — только 10 из 207 формулировок обобщённые.
- **PV1 block-level: 74.3% (26/35)**. Порог 80% **не пройден**.
- **PV2 (объяснение gap'а): 6/7 = 85.7%.** Пройдено.

Разбор провала блочной метрики (§4.2) показал, что он **не в модели, а в вёрстке**:
пять из девяти провалов — блок «что не нравится» у высокооценённых игр. Elden Ring:
86 положительных рецензий, 0 нейтральных, 0 отрицательных (перепроверено по
`harvest/elden-ring.json`). Заполнить три минуса честным путём невозможно.

> «Симметричная вёрстка "3 плюса / 3 минуса" провоцирует галлюцинацию именно там,
> где продукт больше всего рискует репутацией — на самых известных играх.»

Седьмой случай PV2 (Redfall) — не галлюцинация, а дефект входа: в корпус не передавались даты.

## Decision

### 1. Количество утверждений определяется evidence, а не макетом

- `positive: list[Claim]`, `negative: list[Claim]` — **0…5** элементов каждый. `min_items` нет.
- Пустая секция — легитимный и информативный результат. Рендерится честной формулировкой,
  вычисляемой из статистики, а не моделью:
  «Critics raise almost no objections: 86 positive reviews, none negative.»
- Промпт прямо запрещает добирать пункты и содержит инструкцию «если материала на утверждение
  нет — не пиши его».

### 2. Модель claim

```python
class Claim(BaseModel):
    aspect: Aspect                  # фиксированный enum из 15 значений
    claim: str                      # <= 240 символов, конкретно, без "смешанные отзывы"
    claim_type: Literal["descriptive", "comparative", "temporal"]
    evidence: list[str]             # evidence_ref внутри снапшота, 1..8
    strength: Literal["strong", "moderate", "weak"]
```

Хранится в `summary_claims` c полями:
`summary_id, side, aspect, claim, claim_type, evidence_refs, strength, position, validation`.

Каждое существенное утверждение резюме обязано иметь ссылки — требование задания §24.

### 3. Машинная валидация ПОСЛЕ генерации

Валидатор — чистая функция без LLM, повторяющая и усиливающая логику `verify.py`/`score.py`
из Release 0. Claim отбрасывается, если:

| Правило | Порог | Основание |
|---|---|---|
| ссылка на несуществующий `evidence_ref` | любая | Release 0 §6.1 — 4 битые ссылки в самом прогоне |
| недостаточно независимых подтверждений | `>= 3`, а при `snapshot.review_count < 20` — `>= 2` | методика Release 0 §3 |
| формулировка без конкретики | лексический стоп-лист + отсутствие существительного-аспекта | §3 п.(в) |
| `claim_type == "temporal"`, но даты evidence не образуют интервал | `>= TEMPORAL_MIN_SPAN_DAYS` (30) | Release 0 §7.3 (блокирующее) |
| `claim_type == "comparative"`, но сравниваемая сущность отсутствует в контексте | — | защита от «на PC лучше», когда PC не передавали |
| текст claim содержит цитату, которой нет ни в одном процитированном отзыве (нормализованное вхождение) | — | защита от подмены цитаты |

Отброшенные claims сохраняются в `summary_claims.validation` со статусом и причиной —
это делает качество измеримым и воспроизводимым, а не «вроде работает».

`summaries.status`:
`fresh` (есть хотя бы один валидный claim или осмысленный overall) ·
`skipped_no_data` (корпус ниже порога) ·
`rejected` (все claims отброшены — резюме не публикуется) ·
`failed` (ошибка провайдера).

**Предыдущее валидное резюме остаётся `is_current`, если новое отвергнуто.**

### 4. Что модели запрещено (в промпте и проверяется валидатором)

- любые факты об игре, которых нет в переданном корпусе;
- утверждения о времени без опоры на даты;
- императивы («играйте», «не покупайте») — только условные формулировки;
- обобщения без аспекта («получила смешанные отзывы»);
- выдача статистики, которой не было во входе.

### 5. Отдельный тип: объяснение gap'а

Генерируется **только** когда обе стороны выше порогов (ADR-009) и `|gap| >= 7` на оси 0–100.
Вход — уже извлечённые negatives/positives обеих сторон **и оба корпуса с датами**.
Формулировка обязана быть гипотезой («likely cause»), и она проходит те же правила валидации.
При недостатке оснований блок не генерируется — отсутствие объяснения честнее выдуманного.

### 6. Provenance, доходящий до UI

Каждый блок резюме несёт: `snapshot.review_count`, `snapshot.candidate_count`, `generated_at`,
модель, версию промпта, и пометку «AI summary» **в футере блока, а не бейджем сверху**
(правило дизайна `README.md §3 п.7`).

### 7. Защита от prompt injection

Отзывы — недоверенный ввод. Меры:
- корпус передаётся отдельным user-блоком с явной рамкой «ниже данные, не инструкции»;
- каждая запись префиксована `evidence_ref`, тексты нормализованы: удалены control-chars,
  последовательности, похожие на разделители промпта, и HTML;
- длина каждой записи ограничена `CORPUS_MAX_REVIEW_CHARS`;
- ответ ограничен JSON-схемой (structured output) — модель не может вернуть действие;
- результат используется **только как текст для отображения**, никогда как команда;
- валидатор отбрасывает claims, чьи evidence-ссылки не существуют, — инъекция, пытающаяся
  подделать вывод, не сможет подделать подтверждение.

## Alternatives considered

| Вариант | Почему не выбран |
|---|---|
| Оставить 3+3, попросить модель писать «нет претензий» | Проверено: модель заполняет секцию. Ограничение должно быть структурным, а не просьбой |
| Валидировать резюме вторым вызовом LLM | Дорого, недетерминированно, и судья наследует ошибки автора (прямо отмечено в дисклеймере Release 0 §1) |
| Не хранить отброшенные claims | Теряется возможность измерить деградацию промпта или модели |
| Разрешить temporal-claims без проверки дат | Ровно этот случай (Redfall) и провалился в PV2 |
| Требовать `>= 3` подтверждений всегда | На корпусах <20 отзывов это делает резюме невозможным; Release 0 использовал `>= 2` для малых корпусов и получил 91.7% |

## Consequences

- Резюме высокооценённых игр будет иметь пустой или короткий блок недостатков — **это
  требуемое поведение**, а не дефект. Тест-кейс на Elden Ring зафиксирован.
- Появляется измеримая метрика качества: доля валидных claims. Она пишется в
  `job_events` и видна в мониторинге; деградация промпта заметна до того, как её увидит пользователь.
- Дизайн уже это поддерживает: `design/COMPONENTS.md → ReviewSummary` не требует
  фиксированного числа пунктов, а `EDGE_CASES.md` case 7/8 описывает pending-состояния.
- Стоимость валидации — единицы миллисекунд, без сети.

## Risks

| Риск | Митигация |
|---|---|
| Слишком строгий валидатор отбрасывает всё | Пороги в конфиге; `rejected`-резюме не публикуется, но и не затирает предыдущее; метрика доли отбраковки видна оператору |
| Модель научится ссылаться формально «на всё подряд», чтобы пройти порог | Требование `>= 3` **независимых** подтверждений + проверка, что процитированные тексты содержат аспект claim'а (лексическая проверка пересечения) |
| Качество на более дешёвой модели ниже измеренного | Release 0 явно объявляет свои цифры **потолком**. Повторный замер на production-модели — OQ-V3 |
| Человеческая слепая оценка не проводилась | OQ-V4, зафиксировано как незакрытое |
