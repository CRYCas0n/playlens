# ADR-006 — Дедупликация и идемпотентность: гарантии на уровне БД

**Статус:** принято · 2026-09-06
**Подтверждает:** `BLUEPRINT.md` ADR-0007
**Связанные противоречия:** C-02, C-26

## Context

ТЗ требует: игра не обрабатывается дважды за день; уже существующая игра обновляется,
а не дублируется; одинаковые отзывы не сохраняются повторно; два конфликтующих crawler-job
недопустимы; всё это должно работать при нескольких воркерах и переживать перезапуск.

Реализация этих гарантий логикой приложения означает, что каждая из них держится на
отсутствии ошибки в коде. Реализация констрейнтом означает, что она держится на СУБД.

## Decision

**Всё, что может быть выражено констрейнтом, выражается констрейнтом.**

| Гарантия | Механизм | Уровень |
|---|---|---|
| Игра уникальна | `UNIQUE(games.mc_slug)`, `UNIQUE(games.mc_title_id)` | БД |
| Игра обрабатывается ≤1 раза в день | `UNIQUE(crawl_items.crawl_date, game_slug)` + `ON CONFLICT DO NOTHING RETURNING` | БД |
| Активен ≤1 crawl-run | `CREATE UNIQUE INDEX ... ON crawl_runs (status) WHERE status = 'running'` | БД |
| Отзыв не дублируется | `UNIQUE(reviews.game_platform_id, kind, dedupe_key)` | БД |
| Ровно одна lead-платформа | `CREATE UNIQUE INDEX ... ON game_platforms (game_id) WHERE is_lead` | БД |
| Ровно одно текущее резюме | `CREATE UNIQUE INDEX ... ON summaries (game_id, platform_id, audience) WHERE is_current` | БД |
| Задача не выполнится дважды | `UNIQUE(jobs.idempotency_key)` | БД |
| LLM не вызывается на неизменившемся входе | `UNIQUE(summaries.game_id, platform_id, audience, input_fingerprint)` | БД |
| Снапшот корпуса не пересоздаётся зря | `UNIQUE(review_snapshots.game_id, platform_id, kind, content_hash)` | БД |
| Один похожий ряд на игру | `PRIMARY KEY(similar_games.game_id, similar_game_id)` + `CHECK(game_id <> similar_game_id)` | БД |
| Роллапы согласованы с `game_platforms` | Одна транзакция в `GamePersistence.upsert_game` | приложение (осознанно — ради тестируемости; триггер скрыл бы логику) |
| Rate limit к внешним API | Атомарный `UPDATE rate_limits ... RETURNING` | БД |
| Порядок обработки страниц | Курсор `crawl_days.browse_page` | приложение |

### Идентичность игры

Natural key — `mc_slug`. Долговременный суррогат — `mc_title_id` (`product.id`, напр.
`1300501979`): slug может измениться при переименовании, id — нет.

Поиск при upsert: сначала по `mc_title_id`, затем по `mc_slug`. Если найдено по id, а slug
другой — **обновляем slug** и пишем `WARNING game.slug_changed` с обоими значениями.

### Идемпотентный ключ задачи

`{job_type}:{scope}` — например `game.sync:2026-09-06:elden-ring`,
`summary:{game_id}:{platform_id}:{audience}:{fingerprint8}`. Повторная постановка
физически невозможна: `UNIQUE(idempotency_key)`.

Ключ включает дату там, где задача должна выполняться раз в день, и fingerprint там,
где она должна выполняться раз на конкретный вход.

### Различение вставки и обновления без `xmax`

Портируемая двухшаговая операция в одной транзакции (детали в ADR-005 §2). Это нужно,
чтобы честно считать «сколько отзывов реально новых» — вход решения о перегенерации резюме.

### Что происходит при повторном запуске

| Сценарий | Результат |
|---|---|
| Тот же tick запущен дважды | Первый открывает run; второй получает `UniqueViolation` на partial-индексе → `skipped`, не ошибка |
| Игра уже захвачена сегодня | `ON CONFLICT DO NOTHING` → 0 строк → `games_skipped_dupe += 1` |
| `game.sync` доставлен дважды | `UNIQUE(idempotency_key)` отсекает вторую постановку; сам upsert идемпотентен |
| Повторный батч тех же отзывов | `inserted = 0, updated = 0`; `updated_at` не тронут |
| Пересчёт похожих | `DELETE + INSERT` в одной транзакции — идемпотентно и без окна «похожих нет» |
| Повторная суммаризация того же снапшота | `UNIQUE(game_id, platform_id, audience, input_fingerprint)` → вызов LLM не происходит |

## Alternatives considered

| Вариант | Почему не выбран |
|---|---|
| Распределённый лок как основная гарантия | Лок можно потерять (истечение TTL, сетевой раздел, падение хранилища). Констрейнт потерять нельзя |
| Множество обработанных slug'ов в памяти воркера | Не переживает рестарт, не работает при N воркерах |
| Проверка `SELECT ... IF NOT EXISTS` перед вставкой | Классическая гонка: два воркера проходят проверку одновременно |
| Триггеры БД для роллапов | Скрывают логику от тестов и от читателя; отладка сложнее. Выбрана явная транзакция |

## Consequences

- Полная потеря вспомогательной блокировки не приводит к дублям — только к лишней работе.
- Тесты на дедупликацию должны использовать **реальный параллелизм**, а не мок:
  N потоков вызывают `claim_game` на один slug → ровно одна строка.
  На SQLite тест проверяет корректность констрейнта, на PostgreSQL — ещё и поведение
  при конкурентных транзакциях (OQ-V1).
- Все `UniqueViolation` от известных констрейнтов перехватываются и превращаются в
  доменные результаты (`AlreadyClaimed`, `RunAlreadyActive`), а не в 500.

## Risks

| Риск | Митигация |
|---|---|
| Констрейнт забыт в миграции | Тест «схема содержит ожидаемый набор уникальных индексов» — сверка с явным списком |
| `mc_title_id` отсутствует у некоторых игр | Колонка nullable + `UNIQUE` (NULL-ы не конфликтуют); поиск падает на `mc_slug` |
| Slug изменился И `mc_title_id` отсутствует | Создастся новая запись. Ловится sitemap-сверкой и логом `slug_changed`; зафиксировано как известное ограничение |
