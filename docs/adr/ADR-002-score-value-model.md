# ADR-002 — Модель оценки: статус вместо числа, одна ось сравнения

**Статус:** принято · 2026-09-06
**Связанные противоречия:** C-05, C-13
**Отменяет:** `BLUEPRINT.md §6.3` в части «`userscore` — просто `numeric(3,1)`»; `PRODUCT_BLUEPRINT.md §12/§27 R15` в части «никогда не приводить к одной шкале»

## Context

Два независимых факта, оба проверены на первичных данных.

**1. Ноль не означает ноль.** Release 0 обнаружил `userScore: 0` у четырёх игр из двадцати.
Перепроверка всех 21 корпусов `research-fixtures/release0/harvest/*.json` в этой сессии
показала точную границу:

| Игра | Userscore | reviewCount | текстов |
|---|---:|---:|---:|
| NBA 2K27 | 0 | 2 | 0 |
| BioEden | 0 | 1 | 0 |
| Lou's Lagoon | 0 | 1 | 0 |
| Blood Dungeon | 0 | 3 | 1 |
| Diablo Immortal | **0.5** | 6 382 | 3 397 |
| Warcraft III: Reforged | **0.6** | 31 276 | 10 000 |

Ноль при большой выборке в данных не встречается. Ноль при выборке ≤3 — маркер отсутствия
данных. NBA 2K27 при этом имеет Metascore 79: если вывести 0 как оценку, продукт сообщит
заведомо ложное, причём на свежих релизах, то есть на главной странице.

**2. Шкалы разные.** Metascore 0–100, Userscore 0–10. Продуктовый блюпринт запрещает
приводить их к одной шкале; дизайн-пакет (`design/README.md §3 п.1`, non-negotiable)
требует нормализовать `×10` перед сравнением, отображая нативное значение.

Без общей оси невозможны: gap как число, сортировка «biggest critic–player gap»,
консенсус-блок — то есть второй по силе дифференциатор продукта.

## Decision

**Оценка — не число, а значение со статусом.** Одна структура и одна функция на весь продукт:

```python
class ScoreStatus(str, Enum):
    VALID = "valid"              # значение осмысленно
    UNAVAILABLE = "unavailable"  # данных нет; НИКОГДА не рендерится как 0
    NOT_APPLICABLE = "n/a"       # аудитория не оценивает эту платформу

@dataclass(frozen=True)
class ScoreValue:
    raw: float | None        # как пришло от источника, всегда сохраняется
    scale_max: int           # 100 у критиков, 10 у игроков
    review_count: int
    status: ScoreStatus
    low_sample: bool         # review_count < LOW_SAMPLE_THRESHOLD (20)

    @property
    def normalized(self) -> int | None:   # ось 0-100, ЕДИНСТВЕННАЯ ось сравнения
        ...
```

Правило статуса (`app/domain/scores.py`, единственное место в коде):

```
review_count == 0                                             -> UNAVAILABLE
raw is None                                                   -> UNAVAILABLE
raw == 0 and review_count < USERSCORE_ZERO_MIN_RATINGS (20)    -> UNAVAILABLE
иначе                                                          -> VALID
```

Правило тира — тоже одно место, и оно совпадает с `design/prototype/assets/app.js → tier()`:
`>=85 Excellent · 70–84 Good · 50–69 Mixed · <50 Poor · UNAVAILABLE → Not rated`.

**Отображение против сравнения разделены:**

- Отображается **нативное** значение с подписью аудитории: `93 критики` / `8.9 игроки`.
- Сравнивается, сортируется и попадает в gap — **нормализованное** (`8.9 → 89`).
- Рядом с блоком сравнения **всегда** присутствует подпись, объясняющая нормализацию
  и границы тиров (`design/COPY.md §3`, «Always-present axis caption»).

`UNAVAILABLE` в сортировках уходит в конец при **обоих** направлениях — иначе игры без
оценки всплывут первыми при сортировке «по возрастанию».

## Alternatives considered

| Вариант | Почему не выбран |
|---|---|
| Хранить `userscore` как `float\|None`, `None` = нет данных | Не решает главный случай: источник присылает `0`, а не `null`. Информация о том, что это было `0` при `reviewCount=2`, теряется |
| Порог по `user_total_with_text` вместо `reviewCount` | Текстов может не быть при осмысленной оценке (тысячи оценок без текста — норма). `reviewCount` — то, из чего источник считает само число |
| Отбрасывать нулевые значения при сохранении | Потеря данных. Правило подачи не должно менять хранение: если завтра порог окажется неверным, пересчитать из сырых данных можно, а восстановить выброшенное — нет |
| Не нормализовать, показывать две шкалы рядом (позиция продукта) | Убивает gap, сортировку по gap и консенсус-блок. Само возражение продукта («исказит смысл») относилось к подмене **отображения**, а не к вычислению разницы |
| Нормализовать и отображать нормализованное (`8.9 → 89`) | Пользователь не узнает знакомое число Metacritic; ломает узнаваемость и правило дизайна |

## Why

Порог `USERSCORE_ZERO_MIN_RATINGS = 20` выбран не произвольно: в наблюдаемых данных
минимальная настоящая оценка при большой выборке — 0.5, а все ложные нули имеют выборку ≤3.
Порог 20 оставляет запас в обе стороны. Ошибка в консервативную сторону («показали
Not rated игре с честным 0.0 от 20 человек») несопоставимо дешевле ошибки в другую
(«сообщили, что у игры с Metascore 79 оценка игроков 0»).

Разделение raw/status/normalized означает, что правило подачи можно менять одной константой
и пересчитывать историю, а не мигрировать данные.

## Consequences

- В БД хранятся `*_raw`, `*_count` и вычисляемый на чтении статус — миграция не нужна при
  изменении порога.
- API отдаёт оценку объектом `{value, scale_max, normalized, status, review_count, low_sample, tier}`,
  а не голым числом. Шаблоны не могут случайно отрендерить `0`.
- Все сортировки обязаны явно обрабатывать `UNAVAILABLE` (тест на это есть).
- `low_sample` даёт UI право приглушить оценку и поставить пометку — требование J14
  продуктового блюпринта закрывается бесплатно.

## Risks

| Риск | Митигация |
|---|---|
| Настоящий `0.0` при `review_count` между 4 и 19 будет скрыт | Сырое значение сохранено; статус вычисляется на чтении; порог в конфиге. Зафиксировано как известное ограничение в FINAL_AUDIT |
| Нормализация вводит в заблуждение при округлении (`8.94 → 89`) | Округление одно и то же везде (`round(raw * 10)`), в отображении всегда нативное значение, подпись про `×10` присутствует всегда |
