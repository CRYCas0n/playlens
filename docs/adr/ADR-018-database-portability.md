# ADR-018 — PostgreSQL в продакшне, SQLite в разработке и тестах

**Статус:** принято · 2026-09-06
**Уточняет:** `BLUEPRINT.md §6`
**Связанные противоречия:** C-22

## Context

ТЗ §13 требует PostgreSQL со спроектированной схемой, типами, PK/FK/UNIQUE и индексами.
Блюпринт спроектировал схему с использованием `CREATE TYPE ... AS ENUM`, `integer[]` + GIN,
`pg_trgm`, `pgvector` и приёма `RETURNING (xmax = 0)`.

Требование задания §48/§75: каждая фаза оставляет проект в **проверяемом** состоянии;
после каждой фазы прогоняются тесты и миграции.

Среда разработки: Docker отсутствует, PostgreSQL не установлен, свободного места 384 МБ
(portable-дистрибутив PostgreSQL занимает ~1.2 ГБ в распакованном виде). Интеграционные
тесты репозиторного слоя негде запустить.

Проверено в этой сессии: **SQLite 3.45.1 поддерживает все конструкции, на которых держатся
гарантии корректности**:

```
partial unique index                  OK
INSERT ... ON CONFLICT DO NOTHING RETURNING   OK  (вставка -> строка; конфликт -> пусто)
UPDATE ... RETURNING                  OK
ORDER BY ... DESC NULLS LAST          OK
GENERATED ALWAYS AS (...) STORED      OK
```

## Decision

**PostgreSQL 16 — целевая продакшн-СУБД. SQLite — поддерживаемый диалект для локальной
разработки и автотестов. Схема ограничена подмножеством, общим для обоих.**

### Что убрано и чем заменено

| Конструкция блюпринта | Замена | Побочная выгода |
|---|---|---|
| `CREATE TYPE ... AS ENUM` | `VARCHAR + CHECK (col IN (...))`, SQLAlchemy `Enum(native_enum=False)` | Добавление значения — обычный ALTER, а не болезненная миграция enum в PG |
| `platform_ids integer[]` + GIN | полу-джойн `EXISTS (SELECT 1 FROM game_platforms ...)` по индексу `(platform_id, game_id)` | Нет расхождения между массивом-роллапом и таблицей связи |
| `genre_ids integer[]` + GIN | то же по `game_genres(genre_id, game_id)` | то же |
| `pgvector` + `vector(384)` + HNSW | не нужно — эмбеддингов нет (ADR-011) | Минус расширение БД |
| `RETURNING (xmax = 0)` | двухшаговый батч: `ON CONFLICT DO NOTHING RETURNING id` (вставки) + `UPDATE ... WHERE IS DISTINCT FROM ... RETURNING id` (обновления), одна транзакция | Явно и читаемо; тот же результат |
| `pg_trgm` / `tsvector` поиск | абстракция `GameRepository.search_titles()` с двумя реализациями | см. ниже |

Скалярные роллапы (`lead_metascore`, `best_metascore`, `best_userscore`, счётчики) **сохранены** —
они портируемы и дают каталогу чтение без агрегатов.

### Единственное диалект-зависимое место

```python
class GameRepository:
    def search_titles(self, q: str, limit: int) -> list[GameRow]:
        # PostgreSQL: префикс ILIKE + similarity(title_norm, q) (pg_trgm)
        #             + to_tsvector('simple', title_norm) @@ plainto_tsquery
        # SQLite:     префикс LIKE по title_norm + LIKE '%...%'
        #             + ранжирование по позиции вхождения и длине
```

Обе реализации возвращают один и тот же тип и сортируют по одному правилу:
точный префикс → вхождение → `best_metascore DESC NULLS LAST` → `id DESC`.
Нормализация запроса (`lower`, снятие диакритики и пунктуации) — общая, в `normalizers/text.py`,
и покрыта юнит-тестами (`nier automata` → `NieR: Automata`, `assassins creed` → `Assassin's Creed`).

### Миграции

Alembic, автогенерация выключена для критичных объектов: партиальные уникальные индексы
и `CHECK` пишутся явно. Одна цепочка миграций на оба диалекта; условная ветвь только там,
где PostgreSQL получает дополнительное (`CREATE EXTENSION pg_trgm`, GIN-индекс для поиска) —
это **аддитивные** объекты, отсутствие которых в SQLite не меняет логику, только скорость.

### Тестирование

- Полный интеграционный набор гоняется против SQLite в CI и локально — **всегда**.
- Тот же набор гоняется против PostgreSQL, если задан `TEST_DATABASE_URL` (в CI —
  сервис-контейнер `postgres:16`). Без переменной эти прогоны помечаются `skipped`
  с явным сообщением, а не молча пропускаются.
- Отдельный тест сверяет **список ожидаемых уникальных индексов и CHECK-констрейнтов**
  с фактической схемой — чтобы гарантия не исчезла при рефакторинге миграции.
- Тесты на конкурентность (N потоков захватывают одну игру) на SQLite проверяют корректность
  констрейнта; поведение при конкурентных транзакциях PostgreSQL — **OQ-V1**.

## Alternatives considered

| Вариант | Почему не выбран |
|---|---|
| Только PostgreSQL, интеграционные тесты пропускать локально | Репозиторный слой, дедупликация, идемпотентность и очередь ушли бы в продакшн ни разу не выполненными. Это главный риск проекта, а не удобство |
| Только SQLite | Не выполняет требование ТЗ §13 и не выдерживает конкурентную запись при нескольких воркерах |
| ORM-абстракция «поверх любой СУБД» | Приводит к наименьшему общему знаменателю и к потере `ON CONFLICT`, партиальных индексов и `SKIP LOCKED` — то есть ровно тех вещей, на которых держатся гарантии |
| Поднять PostgreSQL из portable-архива | ~1.2 ГБ при 384 МБ свободных. Невозможно |
| `pglite` / встроенный PG | Нет рабочего варианта для Windows/Python |

## Consequences

- Схема немного «беднее» PostgreSQL-идиом, но каждая потеря компенсирована и обоснована.
- `FOR UPDATE SKIP LOCKED` (очередь, ADR-003) — диалектная ветка: в SQLite захват задачи
  выполняется одним `UPDATE ... WHERE id = (SELECT ... LIMIT 1) RETURNING`, что корректно,
  поскольку SQLite сериализует записи. Одна функция, две реализации, оба пути покрыты тестами.
- SQLite в тестах включает `PRAGMA foreign_keys=ON` — иначе FK не проверяются и тесты врут.
- Прогон против PostgreSQL — **обязательный gate перед продакшном**, зафиксирован как OQ-V1
  и как шаг в `RUNBOOK.md`.

## Risks

| Риск | Митигация |
|---|---|
| «Работает на SQLite, ломается на PG» | Никакого сырого диалектного SQL вне двух изолированных функций; SQLAlchemy Core для всего остального; CI-джоб против `postgres:16`; тест сверки схемы |
| Разное поведение при конкурентности | Явно признано: SQLite проверяет констрейнты, PG — конкурентность. OQ-V1 |
| Разные планы запросов → разная производительность | SLO измеряются на PostgreSQL; на SQLite измеряется только корректность |
| Разная семантика типов (даты, decimal) | Все таймстемпы — timezone-aware UTC на уровне приложения; оценки хранятся как `Numeric` и приводятся в домене; покрыто тестами round-trip |
